Caveats: (a) OmDet and Florence-2 latencies measured with a sibling agent's process holding 5.6-6.0 GB resident (a venv313 python cycled 1-18.5 GB all afternoon; tolerated, never killed) — bias is AGAINST OmDet, so 43.5 ms is an upper bound; all other rows measured quiet at ~930 MiB. (b) OmDet's 11/69 sim-person hits were verified by eye: all scores 0.10-0.18, capsule-shaped flickers at its operating threshold — not usable detections; the W-1 "world is the blocker" finding STANDS for the person class. (c) LLMDet-tiny is pipeline-suspect, not an architecture verdict: its sibling llmdet_base scores normally through the identical wrapper, but tiny's person scores are miscalibrated (median 0.149, no threshold separates true from junk — R@P30 tops at 0.035); a first-run scoring bug (empty text spans substring-mapped to "person") was found and fixed; treat LLMDet-base as LLMDet's representative number. (d) Florence-2 emits no confidence scores and phrase-grounding returns few boxes per phrase in crowds — structurally not a detector-seat model. Latency n=25 per cell, so p95 is noisy. Fixed-input models (OWLv2 960^2, OmDet 640^2, GDINO 800, Florence 768^2) are input-resolution-independent; only YOLO rows genuinely speed up at 640x360. Real-photo set is a COCO-val capability control — GoldG/O365-trained candidates (all non-incumbent detectors here) are likely flattered on it relative to OWLv2; no Parcel field claim.
