
Four decisions, each with the measurement or rule that forced it:

1. **One geom carries the prefix, not three.** `city_semantics._instance_id`
   returns the geom NAME for any class it does not special-case, so
   `door_1_jamb_l`, `door_1_lintel`, … would each become a separate `door`
   instance and every door mission would ground AMBIGUOUS. The wall stubs are
   therefore unclassified scene furniture, like `window_*` and `curb`. Seed S6
   proves this: giving one stub the `door_` prefix reddens the one-instance pin.
2. **Sited at the block's west end.** `default_dynamic_agent_specs` routes no
   pedestrian west of x = −3.8 on the north sidewalk (ped-1 and ped-2 turn at
   x = 0.8, ped-3 crosses at x = 3.15, ped-5's loop is x ∈ [−1.4, −0.4]). The
   nearest scripted waypoint to the leaf is well outside its 1.724 m approach
   band; that is a test, not a claim (`test_the_portals_approach_band_is_clear_of_the_pedestrian_routes`),
   and seed S7 re-sites the leaf to x = 1.5 to prove it bites.
3. **y = 4.12, inside the derived sidewalk polygon (2.2 … 4.2).** The threshold
   is standable ground, so "do not stop in the doorway" is a claim about
   reachable geometry rather than about a wall. Extraction confirms
   `support_label: sidewalk`.
4. **`kind: object` in the sidecar, and the note says why.** See §3, R14-D0.

## §3 — What the world proved. Five findings, all REPORTED, none patched

The card: *"a code defect found here is REPORTED, not patched."* Every one of
these has a witness in `tests/test_portal_world.py` that goes **red when the
defect is fixed**, and each witness names itself and says it must be deleted

### R14-D0 — the card's work item 1 is not expressible

The card asks for *"a `portal`-class entry in the scene semantics sidecar."*
`scene_semantics.CLASS_KINDS` is `frozenset({"object", "region"})` and the
schema has exactly two prefix tables (`geom_prefixes` → object,
`region_prefixes` → region). **A sidecar cannot say "portal" today.** Adding a
third kind means editing `src/parcel_robot/scene_semantics.py`, which is neither
in OWNS nor forbidden — I left it alone because the portal SEMANTICS already
live one layer up in `arrival_semantics.ARRIVAL_TABLE`, which classifies the
WORD, and duplicating that judgement into the scene file would have created the
second authority the sidecar's own header forbids. The class is declared
`kind: object` and the file says all of this in place. **This is a deviation
from the card's literal wording** and it is the first thing an auditor should
check.

### R14-D1 — the hosted lane files the door as furniture *(created by this world change)*

`arrival_semantics.classify_place` checks the caller-supplied scene vocabulary
as a WHOLE PHRASE before it checks `PORTAL_WORDS` against the head noun:

```python
if phrase in region_vocab: return CLASS_REGION
if phrase in object_vocab: return CLASS_OBJECT     # <- wins
head = nouns[-1]
if head in PORTAL_WORDS:   return CLASS_PORTAL     # <- never reached for "door"
```

`semantic_goal_from_directive` strips the leading article
(`re.sub(r"^(?:the|a|an)\s+", "", query)`), so the owner's "go to the door"
arrives as the bare token `door`. The moment the sidecar declares a class of
that name, the token matches and the place is an **object**.

Measured on the two real lanes:

| Lane | vocabulary passed | `place_class` | `do_not_cross` | `ask_hint` |
| --- | --- | --- | --- | --- |
| `agent.py` typed panel, `brain/router.py` | none | `portal` | **True** | the ask |
| `runtime._realtime_navigate` (hosted `navigate_to`) | `_realtime_scene_vocabulary()` | **`object`** | **False** | **""** |

The extension mechanism ("let a scene declare a class this module never heard
of") is implemented as an override, so it silences the module's own knowledge.
The consequence is not theoretical: §5.3 shows the live model losing the ask on
exactly this fact. And the live model sent `place: "door"` — the bare token —
so nothing about this depends on my reading of the stripping regex.

**It is this card that armed it.** Before R14 no scene supplied the word.

### R14-D2 — the do-not-cross guard has no polygon to test

`pipeline._apply_arrival_etiquette` (line ~3194):

```python
if do_not_cross and result.polygon and point_in_polygon((pose.x, pose.y), result.polygon):
```

`semantic_candidates_from_observation` builds region dicts with `polygon` and
object dicts with `position` + `metadata` and no polygon at all; `_candidate`
reads `polygon` off the top level, so an object candidate's polygon is always
`()`. A portal is necessarily object-kind, because `ObservationSemanticMap`
filters on `candidate.kind == goal.kind` and the portal row's goal kind is
`object`. **The guard's precondition is never met on the product path.**

R10's `tests/test_arrival_etiquette_pipeline.py` passes because it constructs
`SemanticCandidate(..., polygon=DOOR_POLYGON)` with a rectangle invented in the
test file. My own `test_a_terminal_inside_the_real_doorway_is_refused` uses the
REAL leaf footprint — better geometry, same structural gap — so I also pin the
CONSEQUENCE: hand the guard the candidate the runtime would really build, with a
pose squarely inside the leaf, and it waves the pose through.

The no-cross behaviour that §5.1 measured is therefore real but
**differently caused**: it holds by the `near` band's arithmetic (a band pose is
outside the leaf by construction), not by the guard written to enforce it.

### R14-D3 — `near` is two geometries wearing one name *(pre-existing)*

The planner's arrival authority is a centre-distance band built with the
anchor's **circumscribed** radius, `[r + 1.12, r + 1.32]`. The verifier
(`_semantic_arrival_verified`, relation `near`) re-expresses it as a LiDAR
surface band by subtracting the same radius and the footprint —
`[0.80, 1.00]`, a constant. That subtraction is the disc identity, exact only
when the anchor is round. Measured over the shipped anchors:

| anchor | aspect | r | r − short half-extent | both bands satisfiable head-on |
| --- | --- | --- | --- | --- |
| `lamp_post_1/2` | 1.00 | 0.0600 | 0.0000 | yes |
| `planter_1/2` | 1.00 | 0.4500 | 0.0000 | yes |
| `tree_1/2` | 1.00 | 0.5800 | 0.0000 | yes |
| `bldg_1` | 1.20 | 2.3431 | 0.8431 | **no** |
| `bench_1` | 3.18 | 0.7338 | 0.5138 | **no** |
| `door_1` | 6.67 | 0.4045 | 0.3445 | **no** |

Live control missions through the identical shipping path, same rig, same day:

```
go to the lamppost   arrived / arrived_verified            (round)
go to the planter    failed  / semantic_arrival_verification_failed
go to the tree       failed  / navigation_no_progress   — and it grounded lamp_post_1
go to the bench      failed  / semantic_target_unreachable
go to the door       failed  / semantic_arrival_verification_failed
```

**One of five shipped object classes can be navigated to and verified.** The
door did not break this; the door is the case sharp enough to make it
undeniable, and it is the case that matters because the portal row's terminal
relation IS `near`. Enumerated at 5 mm over the approach half-plane, **9906
poses satisfy both predicates, 4953 of them on the supported sidewalk** — so
this is a pose-SELECTION defect (the planner optimises one predicate and is
graded on another), not impossible geometry. That is a much cheaper fix than it
looks, and it is not mine to make.

### R14-D4 — the rig's obstacle set is a second, unsynchronised scene vocabulary

`headless_city._STATIC_OBSTACLE_PREFIXES` is a hand-maintained tuple of geom
prefixes with no connection to the sidecar's prefix table. `door_` is not in it,
so the block's only portal casts no LiDAR return and joins no collision count in
the quality rig. Measured rather than assumed: splicing `door_` in at runtime
changes the mission's outcome by nothing at all (same pose, same reason),
because D3 rejects the terminal either way — which is why this is filed
separately instead of being blamed for D3.
